Implementation Notes — Phase 3

Review Triage · 2026-07-31 · Review surfaces: the collapse boundary, the notice, the truncation banner

Web tests — a DOM, opted into per file

Context
The spec requires two component test files, collapse-render.test.tsx and chapter-precedence.test.tsx. This started as a no-DOM implementation (vitest in the node environment, renderToStaticMarkup, rules asserted as functions in lib/collapse.ts), and review cycle 1 showed why that was the wrong call: the case it could not cover — a decision arriving on an already-mounted chapter — was where the phase's headline bug lived, so the coverage gap was load-bearing rather than cosmetic.
Decision
Added happy-dom as a web devDependency and opted into it per file with // @vitest-environment happy-dom in chapter-precedence.test.tsx, which now mounts a real Chapter through react-dom/client and drives the two levers the live paths pull: the decision prop and the store's chapterStates. The header carries aria-expanded (correct for an element that already had role="button", and the same attribute the outline variant already sets) so state is queryable without a styling assertion. The pure-function assertions stayed — they are the cheapest way to state the precedence rule.
Alternative
Setting test.environment: 'happy-dom' for the whole package — rejected, and vite.config.ts now pins 'node' with the reason: the store's safeStorage no-ops without a localStorage global, so durable-review-state.test.ts installs a Map-backed shim by assigning globalThis.localStorage, which a DOM environment already owns as a read-only accessor. Also rejected: @testing-library/react, whose whole surface is unnecessary for one component and six transitions.

capStats — nothing populated it, on either server

Context
The spec requires capStats in the /api/narrative response and a promptCapStats test, but ServerContext had no field for it, cli.ts:386 read only result.narrative and result.provider (dropping result.capStats), and cli.ts is not in the Modified Files list. On the daemon side daemon.ts destructured { narrative } and discarded the stats, and ReviewUnit had no field — so the drill-in could not show the banner at all, while the spec's manual test demands parity with the CLI review.
Decision
Added ServerContext.capStats (set at both generation sites, nulled on a cache hit) and ReviewUnit.capStats, assigned unconditionally by attachReview so a cache-hit hydrate clears the previous run's stats rather than describing the wrong generation. The decision log's "compute at serve time, never persist" applies to collapse, whose snapshot warms and cools independently of the unit; capStats describes the generation that produced the narrative beside it and is valid for exactly as long as that narrative is.
Alternative
Leaving the field unpopulated to keep the file list literal — rejected: the required test would then pass against something no real review path ever sets, and the daemon banner would never appear.

Repo context — resolved outside the request, not inside it

Context
Collapse selection needs a RepoContext. resolveRepoContext is a cache read when warm and a whole-tarball download when cold (cap 500 MB, staleness bound 24 hours), and /api/narrative is the page's bootstrap. cli.ts resolved one already, but only on the generation path — a cached narrative skips it entirely, which is the common case for re-opening a PR.
Decision
The CLI server never resolves inside a request. cli.ts hands over the snapshot it already has, the regenerate path updates it, and the cached path kicks off one background refreshRepoContext() whose result is pushed over a new collapse SSE event. A response with no snapshot answer omits collapse entirely, which the web reads as "not checked" — distinct from {available:false}, "checked and could not tell".
Alternative
Awaiting resolution in the handler (what the spec implies for the daemon) — rejected for the CLI: a stale snapshot would stall first paint on a download. The daemon route does resolve per request, as the spec requires, because a unit minted against a cold snapshot must start collapsing once it warms; the Stretch prefetch exists to keep that read warm.

The unavailable notice covers four reasons, not two

Context
The spec gives copy for size-cap and fetch-failed. The union is four members — extract-failed and empty-tree as well — because CollapseUnavailableReason is Extracted from RepoContext, and Phase 1 added empty-tree precisely so "nothing imports this" and "no index" never render alike.
Decision
COLLAPSE_UNAVAILABLE_TEXT is a Record over the whole union, mirroring the CLI's UNAVAILABLE_REASON_TEXT, so a fifth reason is a type error rather than a blank message. All four are covered by the render test.
Alternative
Two cases plus a generic fallback — rejected: a bare "unavailable" is the dead chrome the phase's own key decision rules out.

The divider is gated on the chapters story structure

Context
storyStructure has three values and only chapters has a collapsed state: outline keeps its own per-chapter open flag and linear always renders the body. The spec's divider sketch does not mention the setting.
Decision
The divider renders only under chapters. Drawing a "4 chapters below" boundary above four fully expanded chapters would promise a compression the reader is not getting. The reason line lives on the collapsed row, so it follows the same branch.
Alternative
Teaching the other two structures to honor a decision — rejected as scope: outline already collapses everything but the first chapter (collapse adds nothing there) and linear exists specifically to show everything.

Stretch caller list — placed in the chapter body, not on the evidence line

Context
The stretch says to "include the caller paths on the risk payload the server already sends" and add a disclosure to "the evidence line in Chapter.tsx", while also saying it is only meaningful on non-collapsed chapters. There is no risk payload (the web had no reference to risk at all), and the evidence line this phase adds exists only on collapsed rows — where the caller count is zero by construction, since that is the evidence.
Decision
The servers send a new callers array (chapterCallers in narrative/collapse.ts, same index and same exclude set as the collapse evidence, capped at six with the total kept whole). The disclosure renders at the top of the chapter body, which is visible immediately on a non-collapsed chapter, empty on a collapsed one, and cannot fight the header's collapse toggle the way a <details> inside a clickable row would.
Alternative
A disclosure beside the collapsed row's reason — rejected: it would only ever appear for test-only and generated chapters, and never for the case the stretch describes.

Collapse is cleared by every path that replaces chapters

Context
CollapseDecision.chapterIndex indexes the chapter array the server computed it against. applyPlan, applyPartialNarrative, setData and a unit switch all replace chapters, and the store already documents this hazard for reviewed-state ("carrying ch-${idx} entries across a plan that reorders chapters would transfer 'reviewed' to the wrong chapter").
Decision
All four clear collapse, callers and capStats; callers that hold a fresh result call setBlastRadius immediately afterwards. Both servers' narrative broadcasts now carry a recomputed result, so a regeneration replaces the boundary instead of dropping it.
Alternative
Re-keying decisions by chapter title or content — rejected: the server already knows the answer for the new array, so recomputing is both cheaper and correct.

Known limitation — the banners live inside the story view

Context
The spec places both banners in StoryView.tsx. App.tsx and UnitReview.tsx mount StoryView, ClassicView or RecapView behind a tab, so a reviewer reading raw files on the Files tab sees neither.
Decision
Followed the spec and left them in StoryView. Both layoutMode values and all three story structures share that body, so only the tab switch loses them.
Alternative
Hoisting a notices strip above the tab switch in both hosts — the better home for a fact about the whole review, and a one-line change in each, but it puts the phase's most prominent chrome in two files the spec does not list. Flagged here for the review rather than taken unilaterally.

Snapshot prefetch runs inside the poll pass

Context
The stretch asks for a prefetch after the poll resolves units, best-effort, deduplicated by repo, and bounded by the staleness window.
Decision
prefetchRepoContexts is started (not awaited) at the end of pollNow, keyed by owner/repo@ref, sequential, and guarded by one in-flight flag per wiring. Not awaited because POST /api/poll awaits pollNow for its toast counts, and a cold cache across a dozen repos would leave that button spinning for minutes. The flag matters because the interval poller and the manual route share one pollNow, so overlapping passes would race two downloads of one tarball. resolveRepoContext never throws and no-ops inside its staleness bound, so "best-effort" and "bounded" come for free. One summary log line per pass.
Alternative
A separate timer — rejected: a second schedule to reason about, for a job that has exactly one natural trigger.

Seeding the collapsed state was not enough — the decision arrives after mount

Context
The spec says to seed collapsed in useState and warns against a second effect that writes it, and this was implemented literally. Review cycle 1 found that on both live paths the decision lands after the chapters have mounted: the streaming path mounts placeholders from applyPlan under ch-${idx} keys, so React reuses those instances when the finished narrative replaces the array, and a cached narrative gets its boundary from the collapse SSE event. Collapse therefore applied only on a reload, and the common paths rendered the divider above four chapters that were all still expanded — the exact dead chrome this phase exists to avoid.
Decision
Two fixes, because either alone leaves a window. First, every path that has both a narrative and its blast radius now commits them in one set: setData and applyUnitToStore take an optional BlastRadius, so no render sees new chapters beside stale or absent decisions. Second, Chapter mirrors the existing prevReviewed discipline with a prevHadDecision ref that writes collapsed only on the undefined → defined edge, gated on a touched ref set by the header's click and keydown handlers. Two effects, both edge-triggered, neither able to fight the other. reviewed is deliberately not gated on touched: marking a chapter reviewed is the reviewer acting, and it outranks whatever they did to the chevron a moment earlier.
Alternative
Keying the chapter list so a collapse change remounts every chapter — rejected: it would also discard scroll position, open comment composers, and narration overrides on every SSE tick that carried a boundary.

The truncation banner was styling itself with tokens that do not exist

Context
TruncationBanner used --yellow-2 and --yellow-a5. The scale in index.css defines only --yellow-3 and --yellow-11, so the surface the spec calls "the more serious of the two" rendered as bare text with no background and no inset border, in both themes.
Decision
Switched to the defined --amber-2 / --amber-a5 / --amber-11 triple (present in both :root and .dark), matching how the sibling RegeneratingBanner uses --purple-2 / --purple-a5. The -11 values are identical between the two families, so the text colour is unchanged.
Note
The same undefined --yellow-2 / --yellow-a5 pair is used by pre-existing chrome (MissingHunkBanner and CALLOUT_STYLES.concern in Chapter.tsx). Left alone as outside this phase's diff, but it is a real one-line cleanup for whoever touches those next — or an argument for defining the missing steps in the scale instead.

Two narrower fixes from the same review cycle

SSE replay
/api/events replayed narrative-progress on connect but not collapse, so a snapshot resolving in the window between the bootstrap GET /api/narrative and the browser's SSE connect was dropped with no recovery short of a reload. The start callback now sends blastRadius() as a collapse event when ctx.repoContext && ctx.narrative, covered both ways in server-sse.test.ts — the absent-snapshot case must still send nothing, because "not checked" is a different claim from "checked and could not tell".
Prefetch scope
The prefetch pass took store.list() unfiltered, so a repo whose every unit was already approved, changes-requested, or done still had a base-branch tarball resolved. Now store.list({ status: 'queued' }): the justification is "warm the snapshot the drill-in will need", and a decided unit has no drill-in ahead of it to pay for a download.
