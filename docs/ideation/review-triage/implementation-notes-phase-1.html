Implementation Notes — Phase 1

Review Triage · 2026-07-31 · Repo snapshot and import index

Repository snapshot — in-process tar reader instead of a tar subprocess

Context
Step 4 names Bun.spawn(['tar', '-xzf', '-', '-C', dest]), and separately requires (a) validating every entry before extracting, (b) checking the size cap against a running total of extracted bytes, and (c) building the import index during the same pass over files already being written. A subprocess cannot deliver any of the three: the response body is single-use so it cannot be listed then extracted, bytes fed to tar's stdin are still gzipped, and files written by tar would have to be read back off disk to be indexed. tar -tvf link-target parsing also differs between bsdtar (local) and GNU tar (CI), which the scout flagged as a real divergence.
Decision
Added packages/cli/src/repo/tar.ts — a streaming ustar reader with GNU L/K and pax x long-name support, header-checksum verification, and GNU base-256 size fields. The gzip layer is DecompressionStream('gzip'), so the byte ceiling is enforced on decompressed bytes and a cap breach cancels the stream mid-download. Validated against a real git archive tarball of this repo (307 entries, 3.8 MB): 200 source files indexed in 75 ms, correct root after stripping the wrapper directory. This is one file more than the spec's New Files table lists, and the deviation is deliberate: the spec's own step 4 requires behavior a subprocess cannot provide. Because it adds security-sensitive parsing surface the spec did not budget for, the long-name and corrupt-header branches — the ones every real git archive tarball exercises, since any path over 100 bytes gets a pax extended header — are covered by tar entries synthesized byte-by-byte in repo-snapshot.test.ts (describe('tar reader long names and corrupt headers')) rather than by a committed binary fixture, so the bytes under test are readable in the diff. Both committed fixtures carry only short ustar names.
Alternative
Buffer the decompressed tar to a scratch file, run tar -tf to validate names and tar -tvf to scrape name -> target for symlinks, then tar -xf. Rejected: the scrape is brittle across tar flavors, it costs a full extra write plus two extra passes, and it still leaves the index needing a separate disk walk.

Repository snapshot — 'empty-tree' added to the unavailable reasons

Context
The failure-mode table requires filesScanned === 0 to map to available: false, but the declared union only allows 'size-cap' | 'fetch-failed' | 'extract-failed'. None of the three describes a successful fetch of a tree with nothing in it.
Decision
Added a fourth member, 'empty-tree', rather than overloading 'extract-failed'. Phases 2 and 3 render this discriminant, so the distinction between "extraction broke" and "there is genuinely nothing to index" is worth a surface string. describeRepoContext() in the same module owns the user-facing wording for all four. Downstream contract: the union is now 'size-cap' | 'fetch-failed' | 'extract-failed' | 'empty-tree'. Phase 2's spec restated the three-member version in CollapseResult; that restatement has been corrected in spec-phase-2.md, and any renderer switching on the reason must cover the fourth case.
Alternative
Reuse 'extract-failed'. Rejected: it would tell a user their download is broken when it worked perfectly, and it is the sort of ad-hoc collapse that becomes permanent once a UI reads it.

Repository snapshot — cacheDir on SnapshotOptions

Context
SnapshotOptions as specified exposes only maxBytes and maxAgeMs, yet four required tests (no-second-fetch, stale-refetch, refetch-failure-serves-cached, corrupt-index-rebuild) need control over where snapshots land, and none of them should write into the developer's real ~/.cache/diffdad/repos.
Decision
Added cacheDir?: string, defaulting to repoSnapshotDir(). This is the same affordance migrateLegacyData({ from, to }) already establishes in paths.ts, so it reads as house style rather than a test hook.
Alternative
Point HOME at a temp directory for the duration of each test. Rejected: it mutates process-global state that other suites in the same Bun process also read.

Repository snapshot — owner as its own path segment, and refetch on ref change

Context
The spec sets the cache key to {owner}-{repo} with the ref in a sidecar. Flattening is ambiguous (a-b/c and a/b-c both give a-b-c), and the spec does not say what happens when the sidecar's ref differs from the requested one.
Decision
Layout is {cacheDir}/{owner}/{repo}/ holding tree/, meta.json, and index.json; both segments are sanitized so a .. owner cannot walk out of the cache. A requested ref that differs from the cached one refetches — the spec's stated objection is to per-SHA keying thrashing on every push to the base, and a different base branch is a genuinely different tree, which also gives the sidecar's ref field a purpose beyond decoration.
Alternative
Serve a main snapshot for a release/2 request since caller counts "tolerate drift". Rejected: that is not drift, it is a different tree, and RepoContext.ref would then be reporting something the index does not reflect.

Repository snapshot — symlinks are validated, then never materialized

Context
Validating that a symlink's target stays inside the destination is necessary but not sufficient: the classic escape is a safe-looking symlink (foo -> ../.. relative to a deep directory, or any link to a directory) followed by a later file entry written through it.
Decision
Reject the whole archive on any escaping link target, and skip creating even the links that pass. Nothing downstream reads links — the index walk explicitly does not follow them — so refusing to write them makes write-through-a-symlink structurally impossible rather than merely checked for.
Alternative
Materialize validated symlinks and rely on the path check to catch the follow-up entry. Rejected: the follow-up entry's own path is textually innocent, so the path check cannot see it.

Repository snapshot — a remembered negative, and a wider source-extension set

Context
Only successful snapshots were recorded on disk, so 'size-cap' and 'empty-tree' re-downloaded the entire tarball on every review of that repository, forever. The extension set compounded it: a C, Elixir, Clojure, SQL, or Terraform repository matched nothing, scanned zero files, resolved to 'empty-tree', and paid a full-tree fetch per run to be told so again.
Decision
An unavailable.json sidecar records repo-shaped negatives under their own shorter bound (negativeMaxAgeMs, default 6h against the tree's 24h) and is cleared on the next good fetch. Only 'size-cap' and 'empty-tree' are remembered — both are properties of the repository rather than of one attempt. 'fetch-failed'/'extract-failed' are deliberately not sticky, because a 403 from rate limiting must be retried, not cached. SOURCE_EXTENSIONS gained the C family (headers included), BEAM, Lisps, ML/Haskell/Julia/R, JVM extras, Perl, and sql/tf/hcl/proto. A file scanned for nothing costs one regex pass; a language left off the list costs that repository the whole feature.
Alternative
Remember every unavailable reason under one bound. Rejected: a transient network failure would then suppress repo context for hours, which is the same invisible degrade in a new place. Also rejected: leaving a rejected extraction's directory strictly empty, as the error table implies — the marker is one small file in it, and the tree itself is still removed.

Repository snapshot — eviction also reclaims scratch and sidecar-less directories

Context
Eviction read meta.json and skipped anything without one, so a .tmp-* tree orphaned by a killed extraction, or a repo directory whose sidecar never landed, was never reclaimed — the exact disk-exhaustion mode the 7-day rule exists to prevent.
Decision
Both are now aged out on directory mtime against the same 7-day bound: they have no fetchedAt to read, and the week-long bound is what keeps the sweep safe against a live extraction, whose scratch directory is minutes old rather than days.
Alternative
Delete every .tmp-* sibling on each write. Rejected: the daemon can hydrate two PRs against one repo concurrently, and that would delete a running extraction's scratch tree.

Risk rescoring — both prompt revisions bumped

Context
cache.ts keys cached plans and narratives on PLANNER_PROMPT_REVISION/NARRATIVE_PROMPT_REVISION precisely so a prompt change regenerates stale output, and both entry points short-circuit on that cache before a snapshot is ever resolved (cli.ts's if (cached), the daemon's non-force cache read). This phase changes the prompt contract — inbound=N(repo|diff) plus an interpretation legend, and every risk score moved with the rescaled centrality term.
Decision
PLANNER_PROMPT_REVISION 1 → 2 and NARRATIVE_PROMPT_REVISION 2 → 3. The planner bump is required, not optional: risk hints reach buildPlannerPrompt through buildSharedHeader, so plans change too.
Alternative
Leave them alone since no schema changed. Rejected: every PR already reviewed at the same head SHA would keep serving its diff-only narrative, so the phase would silently do nothing exactly where it is easiest to check.

Import index — text-level import extraction split out of risk.ts

Context
The spec says to reuse IMPORT_RE, extractImports, moduleNameFromPath, and importTargetsFile rather than reinvent them, but all four are module-private and extractImports takes a DiffFile and walks hunk lines — it cannot read a snapshot file's text. IMPORT_RE is also a module-level /g regex whose lastIndex is reset by hand, which the index walk's interleaved awaits would corrupt across files.
Decision
Extracted extractImportsFromText(text) as the shared core and exported it alongside moduleNameFromPath and importTargetsFile. It mints a fresh RegExp per call, so there is no shared match position to corrupt; the diff path now calls it per line and behaves identically.
Alternative
Copy the regex and the two matching helpers into import-index.ts. Rejected: two copies of the project's import-matching rules would drift, and the diff path and the repo path disagreeing about what counts as an import is a silent-wrong-answer bug.

Risk rescoring — K = 20, and repo-wide counts do not exclude the diff

Context
The spec leaves K open, asking only that "~100 repo-wide callers score roughly where 10 diff-internal callers scored before". It also says callersOf takes an exclude set of the diff's paths, without saying whether computeRisk should use it.
Decision
CENTRALITY_WEIGHT = 20, because log10(100) * 20 === 40 — exactly what the old Math.min(refs, 10) * 4 paid at its cap — so centrality keeps its weight against churn and criticality. computeRisk passes an empty exclude set: centrality is about total blast radius, and the spec's own rationale for exclude names Phase 2's "unchanged callers" evidence line as its consumer. With zero inbound refs the rescaled term contributes exactly what the capped one did (both 0), which is what pins the "unchanged ordering without repo context" test.
Alternative
K = 40, doubling centrality's weight. Rejected against the centrality test: it discriminates no better and quietly demotes churn and criticality relative to today.

Risk rescoring — a repo-wide zero is printed, not suppressed

Context
formatRiskHints emitted the inbound token only when inboundRefs > 0. The failure-mode table wants "0 known callers" to stay visible, because the index undercounts (dynamic imports, re-export barrels) and undercounting is the direction that causes a wrong collapse.
Decision
Print inbound=0(repo) when the scope is repo-wide, keep suppressing a diff-only zero (which carries no information), and append a two-line legend telling the model that a repo count is an undercount and that 0 means "no known callers". The spec's Modified-Files row asked only for the scope label; the guard change is what makes the label mean anything at zero.
Alternative
Keep the > 0 guard and only add the suffix. Rejected: the single most decision- relevant case — a widely-changed file that nothing appears to import — would print nothing at all.

Context threading — WriterPromptInput also gained the field

Context
The Modified-Files row for prompt.ts names only NarrativePromptInput, but the third computeRisk call site lives in buildWriterPrompt, whose input type is the separate WriterPromptInput.
Decision
Added repoContext? to both interfaces and forwarded it from writer.ts. Without it the writer pass would have silently kept diff-only counts while the planner pass used repo-wide ones — the exact split-brain inboundScope exists to make visible.
Alternative
Leave the writer on diff-only counts. Rejected: two passes disagreeing about a file's blast radius within one review is worse than either answer alone.
