Implementation Notes — Phase 2

Attention Lanes · 2026-07-31 · Rendering the lanes the daemon already assigns

useUnits / review-store — the dismissed count had no path to the browser

Context
The spec puts dismissedCount inside groupUnits and lists neither the store nor the hooks under File Changes. But phase 1's server splits dismissed units out of the payload (unitsPayload) and all three client ingestion points read only data.units. A filter inside groupUnits would therefore have counted a population that never arrives — a permanent 0, with the unit tests still green because they construct dismissed units by hand.
Decision
Added a dismissed: Unit[] store slice fed from payload.dismissed at all three ingestion points (useNarrative, useUnits, useLiveStream), and useUnits passes [...visible, ...hidden] into groupUnits so the function does the filtering and counting the spec describes. setUnits takes both arrays as required parameters, so a future caller cannot drop the second one by omission.
Alternative
Merging dismissed units into the existing units array. Rejected: everything downstream of units — the repo filter, the facet counts, and the empty state's total === 0 — would begin counting rows that render nowhere, so a queue holding only dismissed PRs would show a non-empty total against a blank page.

Tests — a new file, against the spec's "New Files: None"

Context
The spec declares no new files, but its own validation command is bun run --filter '@diffdad/web' test -- -t "lane render", and the contract requires evidence that no row displays the 0 to resolve placeholder. That is a render assertion; units-view.test.ts is pure and cannot make it. With no matching test the command exits 0 having run nothing, which reads as satisfied.
Decision
Added packages/web/src/components/__tests__/lane-render.test.tsx (12 tests) following the collapse-render.test.tsx precedent — renderToStaticMarkup in the default node environment, since UnitRow is prop-driven. Exported FileTable from UnitRow so the drawer's contents are assertable: its open state needs a DOM the suite deliberately does not have.
Alternative
Opting the file into happy-dom and driving a click. Rejected as more machinery than the assertion needs, and there is no testing-library in the project — the click would have been hand-rolled against a React root.

units/lane.ts — one payload builder instead of two lane attachments

Context
The spec says to extend unitsPayload() in daemon/app.ts and to make "the same attachment" in the poller. The poller's emission is not a call to that helper, though — it is an inline object literal, so following the spec literally would have produced two implementations of the wire shape.
Decision
Hoisted unitsPayload (with its prose) into packages/cli/src/units/lane.ts, which already owns both halves of what it does — laneOf and isDismissed — and called it from both sites. app.ts does not import the poller, so there is no cycle. This is the same argument the contract used to put laneOf CLI-side: the failure mode named in the spec ("a row's lane depends on which message painted it") becomes unrepresentable rather than merely tested.
Alternative
Mirroring the spread in the poller. Rejected — it leaves the ninth emission point free to drift from the other eight.

groupUnits — the verdict rank was kept, not dropped

Context
The spec enumerates three sort keys for needs-you (criticality, then nobody-approved, then oldest-first) and says the oldest-first tiebreak is retained. It is silent on the existing VERDICT_RANK key, which those three would otherwise orphan.
Decision
Retained it as the lowest-priority key above the tiebreak. On unhydrated rows every verdict is neutral, so it costs nothing there — which is precisely why it was never a usable lead signal and why the mockup calls it out. On a PR that has been opened it is a real measurement, and this feature has no business discarding one.
Alternative
Deleting VERDICT_RANK. Rejected: it silently loses signal for hydrated units, and "the spec didn't mention it" is not evidence it should go.

units-view.ts — buildRepoFacets now reads the lane too

Context
Not in the spec's File Changes, but in the same file. buildRepoFacets counts needs-you via groupOf(u.status), which routes every queued unit — probably-not included — into the sidebar count. Its own doc comment promises the count "matches the Needs you lane exactly", and this phase would have made that a lie: a repo showing 5 in the rail beside a lane of 2.
Decision
Switched it to the shared laneOf reader and rewrote the comment to say why. Covered by a test.
Alternative
Leaving it and documenting the divergence. Rejected — two visible counts of "work waiting on you" that disagree is exactly the kind of untrustworthy number this whole feature exists to remove.

UnitRow — reviewer copy is narrower than the mockup's

Context
mockup.html renders "1 of 3 reviewers · none have approved" and "2 of 3 already approved". The wire carries only reviewRollup: { approved, changesRequested } — there is no requested-reviewer total on it, and no "am I the only reviewer" signal. The spec's own reasonLine description omits reviewers entirely, so the two artifacts disagree.
Decision
Rendered only what the rollup supports: "nobody has approved" / "2 approvals already". Took the spec's stricter reading over the mockup's, and asserted the absence in a test (not.toContain('of 3')) so the richer copy cannot creep back in without the data behind it.
Alternative
Fetching and storing the requested-reviewer list to match the mockup. Rejected as new phase-1-side data collection, well outside a rendering phase.

stakesOf — thresholds the spec did not give

Context
The spec specifies the signature and that stakes are visual weight only, but names no numbers.
Decision
Criticality or truncation ⇒ high outright; otherwise high at ≥200 changed lines or ≥10 files, low at ≤20 lines and ≤2 files, mid between. A unit with no triage sits at mid: it is not known to be small, and promoting it to high would make every un-backfilled row shout during the poller's backfill window.
Alternative
Deriving stakes from metadata.changedFiles. Rejected — that field is 0 on search-minted units until hydrate, so it would size the newest rows as the smallest.

reasonLine — where it mirrors the CLI's rule, and what that costs

Context
The failure-mode table forbids recomputing the lane client-side. reasonLine reads the same triage evidence needsYouReason reads, which is adjacent enough to be worth stating plainly rather than leaving for a reviewer to notice.
Decision
Lane membership is read from unit.lane and never derived; the probably-not branch of reasonLine defers to that lane outright rather than re-deriving it. For the needs-you branches the ordering mirrors needsYouReason, and the property that makes this acceptable is narrow and worth naming: each branch states a fact that is true of the PR independent of which branch won, so a drift shows a different true fact, never a false one. A test asserts no reason or drawer sentence ever contains "safe", "fine", or "approved".
Alternative
Putting the NeedsYouReason union on the wire beside the lane. Genuinely cleaner, and worth revisiting if the reason copy grows — rejected here because the union carries no summary for the probably-not case (it is null), so the kind summary would still be computed web-side and the wire would grow for a partial win.

UnitRow — the drawer opens from a chevron, not from the row click

Context
In mockup.html the row's main button toggles the evidence drawer (onclick="toggle(...)", :814) and the › is a passive span; the spec's manual test reads "Click a 'Probably not' row; confirm the drawer lists every file". The real row click already has a load-bearing behavior the static mockup had nowhere to put — it opens the unit's review.
Decision
Kept row click = drill-in and made the › the drawer toggle (rotating 90° when open, with aria-expanded). Raised by the cycle-1 reviewer, which is why it is recorded here rather than passed over: the manual-test step should now read "click the chevron on a 'Probably not' row".
Alternative
Making row click toggle the drawer on probably-not rows only. Rejected — the same gesture would mean two different things depending on which lane a row happened to be in, and lanes move on their own as PRs are re-triaged.

UnitRow — the drawer is offered on every lane, not just the two attention ones

Context
The drawer was first restricted to needs-you and probably-not, which left drawerNote's in-flight/cleared branch unreachable from any component — dead code exercised only by its own test. The cycle-1 reviewer caught it and noted the mockup renders the card on its in-flight row with settled copy.
Decision
Offered it on all four lanes. "Why is this row here?" is a fair question of an in-flight row too, and drawerNote already answers it honestly — "status decides this one, not its files". This matches the mockup and removes the dead branch rather than deleting a truthful answer.
Alternative
Deleting the in-flight/cleared branch of drawerNote. Rejected — it is the correct answer for those rows, and the mockup asks for it.
