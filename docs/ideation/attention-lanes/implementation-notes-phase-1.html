Implementation Notes — Phase 1

Attention Lanes · 2026-07-31 · Triage inputs and the lane function

Dismissed units — split out of the units payload, not just kept in the store

Context
The spec made DELETE /api/units/:id a soft delete so the poller cannot re-mint a dismissed PR, but it never said how a dismissed unit leaves the view. Its manual checklist implies the row disappears in phase 1 ("✕ a row, wait two poll passes, confirm it stays gone"), while its failure-modes table describes the unit as "reachable behind the dismissed count" — a phase 2 affordance. Meanwhile every payload returned store.list() raw, so ✕ kept the unit and the very next SSE frame repainted the row it had just hidden. Shipping phase 1 alone would have made ✕ look broken in a new way.
Decision
Added a single unitsPayload() helper in daemon/app.ts that splits a unit list into { units, dismissed }, and routed every emission point through it (GET /api/units, /api/narrative, all four broadcasts, the SSE bootstrap, and the poller's own post-pass broadcast). Dismissed units ride along under dismissed rather than being dropped, so phase 2's reveal has something to render and a dismissal is never silently unreachable. The existing frontend reads units only, so ✕ works immediately with no web change.
Alternative
Accept the regression until phase 2 lands on the same branch. Rejected: the two phases are separately committable, and a phase whose headline control visibly does nothing is worse than one extra server-side helper. Also rejected: dropping dismissed units from the payload entirely, which would have left phase 2 with no way to build the reveal without a second round trip.

Reviews rollup — narrowed to queued units, narrower than the spec's wording

Context
The spec says to fetch the reviews rollup for "open units" and its failure-mode mitigation says to skip dismissed and cleared ones. It does not say to skip changes_requested (the In flight lane), and the rollup's stated purpose is ordering within a lane — which in principle includes that one.
Decision
Fetch only for status === 'queued'. This is the one genuinely recurring cost in a poll pass — the contract's own G2 puts it at roughly double the API traffic, approaching GitHub's 5000/hr ceiling near forty open units — and an In flight PR is waiting on its author, so its position in a lane nobody is triaging is not worth a request every sixty seconds. Recorded here rather than left as a silent narrowing.
Alternative
Include changes_requested for literal spec conformance. Rejected on the rate-limit budget the contract already made explicit; revisit if In flight ever gains an ordering that depends on approvals.

Scout — unavailable, explored inline instead

Context
execute-spec step 2 dispatches the read-only Scout to map the codebase across five readiness gates and persist a context-map.md. The agent was invoked, went idle twice without returning any output, and did not answer a direct request for its map.
Decision
Proceeded using the skill's documented fallback for an unavailable scout: explore inline by reading the spec's "Pattern to follow" paths and every file in its Modified Files table. Risk was lower than usual because those files — risk.ts, diff-filter.ts, collapse.ts, client.ts, poller.ts, store.ts, linking.ts, app.ts — had all been read directly during the interview that produced the spec. No context-map.md exists for this phase.
Alternative
Block the phase until the scout responded. Rejected: it had already failed twice, and the reviewer agent (which did run, and returned five findings) is the gate that actually protects the commit.
